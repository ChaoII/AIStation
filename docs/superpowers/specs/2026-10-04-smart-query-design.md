# AIStation 智能问数（Text-to-SQL / 自然语言查数）设计方案

> 状态：评审稿（待用户分析确认）
> 定位：归属 AI 管理模块 `module_ai`，新增「智能问数」页。
> 核心诉求：**简单数据问题要「秒级 + 精准」**，不是普通 AI 那种 20~30 秒才出的答案。

---

## 一、目标与设计原则

### 1.1 要解决的问题
让用户用**自然语言**快速查数：
- **本系统数据**：AIStation 自身的业务库（训练任务、告警、设备、用户、请求日志……）
- **自定义数据源**：用户自行配置的外部数据库 / 文件 / 接口数据

### 1.2 核心矛盾
| 矛盾 | 说明 |
|------|------|
| 「通用 NL2SQL」慢 | 每次让 LLM 读 schema + 写 SQL，动辄 10~30s，且准度不稳定 |
| 「模板查数」快但不通用 | 预定义模板只能覆盖高频问题，问法一变就失效 |

**方案结论：不把「慢而通用」和「快但受限」对立，而是做成「语义层 + 双路径」**：高频/简单问题走**快路径**（秒级），低频/复杂问题走 **LLM 慢路径**（精准兜底），并用一套**语义层**统一映射，让两条路径共享同一套「指标/维度/术语」知识。

### 1.3 设计原则
1. **语义先行**：先沉淀「指标/维度/业务术语」资产，再谈 SQL 生成。语义层同时喂给两条路径。
2. **快路径优先**：能走模板就不走 LLM；能走缓存就不用真实查询。
3. **只读 + 权限不绕过**：生成/执行的 SQL 一律只读，且必须叠加租户/数据域/用户权限过滤；不允许用户手写任意 SQL。
4. **可解释**：返回结果时给出「命中模板 / 用到的字段 / 生成的 SQL」，用户可校验。
5. **可迭代**：记录查询历史与用户反馈，反向沉淀语义层与模板，越用越准。

## 二、整体架构

```
┌───────────── 用户输入（自然语言） ─────────────┐
│  意图/实体识别（规则 + 轻量模型）              │
└──────────────┬──────────────────────────────────┘
               │
       ┌───────┴────────┐
       │  语义层匹配      │  ← 指标/维度/术语/模板库
       │  (模板/向量)    │
       └───┬─────────┬──┘
   匹配命中 │         │ 未完全命中
       ┌───┘         └───┐
       ▼                  ▼
 【快路径】模板执行    【慢路径】LLM NL2SQL
 预聚合/缓存/参数化     schema+语义上下文注入
 报表/导出             → SQL 生成 → 校验 → 执行
       │                  │
       └────────┬─────────┘
                ▼
         【查询执行引擎】(只读连接池)
            ├─ 系统库(只读副本/受权限约束)
            └─ 自定义数据源(注册的连接)
                ▼
          统一结果集(表格+自动图表) → 流式/秒级返回
```

### 关键模块
1. **语义层（Semantic Layer）**：数据资产的单一事实来源。
2. **意图路由**：判定走快路径还是慢路径，以及目标数据源。
3. **NL2SQL 引擎**：LLM 生成 SQL（慢路径）。
4. **查询执行引擎**：统一执行 + 限流 + 超时 + 行数上限 + 权限注入 + 结果格式化。
5. **数据源管理**：自定义数据源的注册、连接、schema 同步、测试。
6. **缓存与预聚合**：快路径的命中和加速器。
7. **前端「智能问数」页**：会话式问答 + 结果可视化 + 追问。

## 三、语义层：两条路径共享的「知识底座」（最重要）

> 这是把「问数」做得又准又快的**根基**。没有语义层，LLM 每次都要「从零读 schema 猜语义」，必然慢且飘。

### 3.1 语义层的四类资产

| 资产 | 定义 | 例子（系统数据） |
|------|------|------------------|
| **指标 Metric** | 可量化、可聚合的业务口径 | 今日登录人数、本月告警数、训练任务成功率、平均耗时 |
| **维度 Dimension** | 切分/过滤的字段 | 设备、算法类型、任务状态、日期、租户 |
| **实体 Entity** | 与业务对象绑定的名词 | 「摄像头」「训练任务」「告警规则」 |
| **术语 Dictionary** | 口语/业务叫法 → 字段 | 「在线设备数」→ `camera.online=1` 计数 |

### 3.2 指标的定义方式
每个指标是一段**可参数化 SQL 模板** + **口径说明**，例如：

```yaml
metric:
  key: alert_count_today
  name: 今日告警数
  datasource: system
  sql: >
    SELECT COUNT(*) FROM video_alarm_record
    WHERE created_time >= CURRENT_DATE AND is_deleted = false
  params:   # 可选的参数，如按设备/算法过滤
    - { key: camera_id, label: 摄像头, from: video_camera }
    - { key: alarm_type, label: 告警类型, from: dict }
  agg: count
  unit: 条
```

这样做的价值：
- **快路径直接用模板**（秒级）。
- **慢路径把「指标/维度/术语」注入 LLM 作为上下文**，LLM 只做「口语 → 语义资产 → SQL 片段」的组装，而非从头写 SQL，**准度大幅提升**。
- 指标可**加缓存/预聚合**（见 §十一）。

### 3.3 指标来源
- **系统库**：开发期预置一批高频指标（告警、训练、设备、请求日志、用户等）。
- **自定义数据源**：配置数据源时，可选「自动生成探查指标」或由用户在语义层手动补充指标与术语。

## 四、意图路由：决定「快 or 慢」

### 4.1 第一层：目标数据源判定
- 命中「系统指标/实体」关键词 → **系统库**。
- 命中某数据源名称/其表、字段关键词 → **该自定义数据源**。
- 两者都不明显 → 询问澄清（列出可选数据源）。

### 4.2 第二层：快/慢路径判定
```
规则匹配命中（实体识别 + 指标模板匹配）  →  快路径
向量/语义相似度高于阈值               →  快路径（套用相近模板）
以上都未命中                          →  慢路径（LLM）
```

判定依据：
- **规则层**：术语字典 + 正则 + 指标 key 匹配（0~几 ms）。
- **向量层**：对「指标/模板」做 embedding，线上把用户问句向量化后做相似度检索（几十 ms）。命中 >阈值（如 0.85）走快路径。
- 判定本身**极快**，不消耗 LLM。

> **关键体验承诺**：快路径目标 < 1~2s（含 UI 渲染）；慢路径才进入 LLM 生成。

## 五、快路径（秒级响应）

### 5.1 三种实现层次（按成本递增）
| 层次 | 做法 | 最快 | 适用 |
|------|------|------|------|
| L1 预聚合缓存 | metrics 结果按时间窗口/维度预计算进 Redis/物化视图 | <100ms | 极高频看板类指标 |
| L2 参数化模板 | 模板 + 参数（如时间、设备）直接执行 SQL | <500ms | 高频指标，参数化 |
| L3 模板近似/组合 | 多模板匹配或模板参数抽取组合 | <1s | 中频，接近模板语义 |

### 5.2 快路径流程
1. 语义层匹配到 metric + 解析参数（时间词「今天/本月/最近7天」、实体「xx摄像头」）。
2. 有 L1 预聚合/缓存 → 直接取；否则执行模板 SQL。
3. 结果套统一结果集（列、单位、关联维度标签）。
4. 返回并标记 `source: fast`（前端打「精准命中」角标）。

### 5.3 时间词解析
内置时间词理解：今天/昨天/本周/本月/最近N天/上季度/今年…… 统一转成基于 `CURRENT_DATE` 的相对区间，保证「每次问都能命中当天」。

## 六、慢路径（LLM NL2SQL，精准兜底）

### 6.1 输入上下文（**精准度的关键**）
给 LLM 的上下文**不是全库 schema**，而是「与该问题相关的」最小注入：
- 候选数据源的**相关表 + 字段 + 注释**（由意图/实体检索裁剪，避免 token 爆炸）。
- 相关**指标/维度/术语字典**（让 LLM 复用口径，而非自创）。
- 该数据源的 **few-shot 问答示例**（2~4 条）。
- 明确的**输出约束**（只读、返回 `{sql, params, explain}`、禁止 DDL/DML、`LIMIT` 上限）。

### 6.2 安全与校验
1. **LLM 只生成 SQL 文本，不直接执行**。
2. **静态校验**：仅允许 `SELECT`；拒绝多语句/`;`/注释/`INTO`/`CREATE`；检查只引用白名单表/字段。
3. **AST 解析**（用 sqlglot/sqlparse）确认无 DDL/DML、无子查询滥用、无未授权表。
4. **权限注入**：执行前把当前用户的**数据域**（如 tenant_id、设备组、数据源授权）作为 WHERE 强制拼入。
5. **自纠错**：执行报错则将错误信息回喂 LLM，限 1~2 轮重试。
6. **超时 + 行数上限**（如 LIMIT 1000，超时 10s）。

### 6.3 流式体验
慢路径用 **SSE 分阶段流式**回传：
```
data: {"stage":"parsing"}      // 意图/数据源识别中
data: {"stage":"generating"}   // LLM 生成 SQL 中
data: {"stage":"sql","sql":"SELECT ..."}  // 生成完成，展示给用户
data: {"stage":"executing"}    // 执行中
data: {"stage":"result", "columns":[...], "rows":[...]}  // 结果到达
```
用户**立刻感知到在动**（典型 <1s 出「解析中」），而非干等 20s。

## 七、自定义数据源管理

### 7.1 支持类型
| 类型 | 说明 | 备注 |
|------|------|------|
| PostgreSQL / MySQL | 外部业务库 | 只读账号，连接池 |
| SQLite | 单文件 | 上传/路径 |
| CSV / Excel | 结构化文件 | 上传后自动建表/映射语义层 |
| HTTP API | 外部接口 | 走「指标模板」方式，不生成自由 SQL |

### 7.2 配置项（对齐「配置化易用性」规范）
- 名称/编码、类型、连接串（host/port/库/用户/密码/SSL）、**只读**开关。
- 启用、默认、备注。
- **Schema 同步**：一键拉取表/字段/注释，生成可查目录并写入语义层。
- **连接测试**。
- **权限**：哪些角色/用户可查；可做字段级掩码（如金额、手机号）。
- **指标/术语维护**：为该数据源补充业务指标与术语。

### 7.3 语义层驱动（关键）
数据源接入后，**主要靠它自己补充的指标与术语**，而非让用户面对一堆表写 SQL。文件/API 类数据源尤其如此——它们天然用「指标模板」表达，不生成自由 SQL。

## 八、安全与权限（不可绕过）

| 维度 | 措施 |
|------|------|
| 只读 | 统一从**只读连接/只读账号**发查询；SQL 静态校验 + AST 校验 |
| 本系统数据 | 强制叠加**租户 + 数据域 + 用户数据权限**（复用现有 `__permission_strategy__` 的数据范围），NL2SQL 不能绕过，否则视为越权 |
| 自定义数据源 | 按数据源授权；行级（如库内 tenant 字段）+ 列级掩码 |
| 防注入/枚举 | 只执行白名单表/字段；禁止 DDL/DML/多语句；超时与 LIMIT |
| 审计 | 记录 用户/问句/识别出的数据源/生成的 SQL/结果行数/耗时/是否命中模板 |
| 敏感指标 | 敏感指标设权限标签，无权限用户即使问对也不返回 |

## 九、前端「智能问数」页（用户体验核心）

### 9.1 页面布局
- 左侧：**会话列表**（历史问数）、可切换**数据源/系统库**。
- 中央：**问答流**（用户问 + 助手答）。
- 答案区：表格 + 自动图表（ECharts，按列类型自动选柱/折/饼）；可**导出 CSV / Excel**；可**追问**。

### 9.2 体验设计（对齐「秒级 + 精准」诉求）
| 场景 | 体验 |
|------|------|
| 快路径命中 | **<2s 出结果**，答案带「精准命中」角标，副标题展示所用指标与参数 | 
| 慢路径 | 先秒出「解析中/生成中」**阶段流式**，再「执行中」，最后出结果；全程有进度，不干等 |
| 结果 | 表格 + 自动图表 + 明细可展开；关键数字用 `el-statistic` 卡片高亮（如「今日告警 128 条」） |
| 不确定 | 多数据源/多指标候选时，**给用户选择**而不是瞎猜；答完给「追问/换一种问法」 |
| 空态/无权限 | `el-empty` + 引导；无权限明确提示缺哪个权限 |
| 更正反馈 | 点赞/点踩 + 正确 SQL 回填，沉淀语义层 |

### 9.3 「快」的额外手段
- **冷启动提示**：给出「你可以这样问」的**示例问题**（一键直达快路径模板），降低用户试错。
- **常用问题收藏**。
- 答案**缓存**：相同/相似问句 + 数据未变 → 直接返回（命中缓存也标 fast）。

```
# 数据源管理

# 语义层
GET    /ai/query/metrics?datasource=        指标列表

# 问答
POST   /ai/query/ask                        用户提问 → 返回 { path, result | pending }
POST   /ai/query/ask/stream                 SSE 流式（慢路径分阶段）
```

`POST /ask` 返回示例：
```json
{
  "path": "fast" | "slow",
  "datasource": "system",
  "sql": "SELECT ...",
  "columns": ["日期","告警数"],
  "rows": [["2026-10-04", 128]],
  "metrics": ["alert_count_today"],
  "took_ms": 340,
  "cached": false
}
```

## 十一、表结构设计（草案）

```
ai_query_datasource   # 数据源
  id,name,code,type(db/file/api),host,port,database,username,password_enc,
  read_only,enabled,remark,created_by,tenant_id

ai_query_metric       # 指标
  id,datasource_id,key,name,description,
  sql_template,params(json),dimensions(json),agg,unit,
  cache_ttl,precomputed(bool),permission_tag

  id,datasource_id,term,metric_key? ,field_path,type

  id,datasource_id,table_name,column_name,column_type,comment,is_sensitive

  id,user_id,tenant_id,datasource_id,title,created_time

  id,session_id,question,path,datasource_id,sql,columns_json,rows_json,

```

## 十二、性能与缓存

| 手段 | 说明 |
|------|------|
| 指标预聚合 | 高频指标用 Redis / 物化视图按窗口预计算，L1 快路径 <100ms |
| 参数化缓存 key | `{metric_key, 时间区间, 维度参数, 数据源版本}` 归一化后作缓存 key |
| schema 裁剪 | 只注入相关表的 schema，降低 token、提升准度与速度 |
| 只读连接池 + 索引 | 统一 `async_db_session`/连接池，SQL 强制走索引（时间列建索引） |
| 行数上限 | 结果默认 LIMIT（如 1000），导出走分页/后台任务 |
| 异步慢查询 | 慢路径 > 阈值转后台任务 + 进度推送，避免前端阻塞 |

## 十三、评估与迭代（越用越准）

- **命中率**：快路径命中占比（目标 >70%）。
- **准确率**：SQL 可执行率、结果正确采样核对。
- **响应时间**：快路径 P95 < 2s；慢路径出首阶段 < 1s。
- **反馈闭环**：用户「赞/踩 + 正确 SQL」回填 → 沉淀为**新指标/新模板/新术语**，下一条同样问法直接走快路径。
- 提供**调试面板**：看命中路径、注入的 schema、生成的 SQL、耗时分解，便于治理。

## 十四、分期实施计划（建议）

### 阶段 A（闭环 MVP，先做「本系统数据 + 秒级」）
1. 语义层（系统库预置 20~30 个高频指标 + 术语字典）。
2. 快路径（模板执行 + 时间词解析 + 参数 + 结果表格式）→ **先打通「秒级精准」**。
3. 前端「智能问数」会话页 + 表格/图表 + 示例问题。
4. 慢路径（LLM NL2SQL）+ 安全校验 + SSE 流式。
5. 审计 + 反馈闭环。
> 目标：**本系统高频数据问题 1~2s 内、可复现、精准**。

### 阶段 B（自定义数据源）
6. 数据源 CRUD + 连接测试 + schema 同步。
7. 数据源语义层（指标/术语维护）+ 权限授权。
8. 外部数据源查询引擎（只读池 + 权限注入）。

### 阶段 C（增强）
9. 指标预聚合/物化视图/Redis 缓存。
10. 自动图表 + CSV/Excel 导出 + 仪表盘收藏。
11. 该问数能力嵌入其他模块（如训练、告警、仪表盘）。

## 十五、开放问题（需评审确认）

1. **本系统数据用只读副本还是主库只读连接？** 建议独立只读账号/副本，避免影响主库（本项目已有 postgres + rustfs，可评估加只读副本）。
2. **LLM 由哪个模型驱动？** NL2SQL 建议用**强 SQL 能力模型**（如 qwen-coder/deepseek 类），且与现有 `module_ai` 的模型配置打通；失败可回退到通用模型。
3. **指标口径由谁维护？** 建议产品/运维在「指标运营」后台维护，用户侧只问不写。
4. **自定义数据源的字段级掩码**范围（哪些字段默认脱敏）。
5. **是否允许「语义层自动探查」**（根据数据自动生成候选指标）还是完全人工维护（更稳、更可控）。建议 MVP 人工为主、自动为辅。
6. **缓存一致性**：系统库数据变动频繁时，预聚合/缓存的刷新策略（如 30s~5min TTL 或变更信号失效）。
7. **命名/位置**：菜单放 AI 管理下（如 `/ai/query`），还是独立一级菜单？建议放 AI 管理下做闭环。

---

## 十六、一句话总结

> **用「语义层（指标/维度/术语）+ 快慢双路径」取代「每次让 LLM 裸写 SQL」**：
> 高频简单问题命中模板 → **秒级**；复杂问题由 LLM 生成 SQL + 安全校验 → **精准兜底**；自定义数据源同样走语义层；并且**权限、只读、审计全程不可绕过**，用反馈闭环越用越准。
