## 10. 公平口径的 3 条失败与修复（修完复跑：104/105，仅剩口径题）

| 失败题 | 现象 | 根因 | 处理 |
|--------|------|------|------|
| 按日期汇总每日耗用量… | 返回 `2025-12-14T00:00:00`，金标 `2025-12-14` | `_json_cell` 对午夜时间戳直接 `isoformat()` | 午夜整点（00:00:00.000000）按日期输出；比对侧 `_norm_cell` 同时接受 `T` 分隔 |
| 按收到基低位发热量取前 3 条 | `(NULL, 6200, 6001)`，空值被当成最大值 | PostgreSQL `ORDER BY … DESC` 默认 **NULL 排在最前** | 生成规则第 8 条要求 Top-N 排除空值 + 数值 CAST（已单独验证与金标一致） |
| 入厂煤批次一共有多少条 | 522 vs 577 | 平台自动补 `ISDELETED=false`（只算有效行），金标统计全量 | **保留差异**，需业务确认口径；不为了对齐而改代码 |

> 教训：`ORDER BY 数值列 DESC` 的 NULL 语义是**确定性方言行为**，最终应升级为代码改写
> （SQL 校验层对排序键补非空过滤），提示词只是当前成本最低的落点。

复跑结果：**104 / 105 = 99.05%**，只剩「入厂煤批次总数」（522 有效 vs 577 全量）这一条口径题；
日期与 Top-N 两条已稳定通过（不是单题偶过——整轮 105 题重跑后仍通过）。

## 11. 生成规则可配置（提示词规则从代码搬到库）

原来 8 条生成规则写死在 `nl2sql_ops.py`，改一句话要发版、也无法按数据源区分。
现在：

- 表 `ai_query_prompt_rules`（启动幂等建表 + 播种，**不覆盖**已改文案）：
  `code / title / body / scope / scope_value / source_setting / enabled / priority / is_core / is_custom`
- 读路径 `prompt_rules.render_rules(cfg, datasource, dialect)`：
  - 按 `priority` 排序、按 `enabled`/作用域过滤，**编号在渲染时统一生成**（停用不跳号）；
  - `source_setting` 复用已有开关（`entity_name_rule` / `enum_hint_enabled` / `decomposed_planning`），
    开关决定「要不要」，表决定「写什么」；
  - 读库失败回退代码默认文案 —— **配置坏了不影响问数**。
- 接口：`GET/POST/PUT/DELETE /ai/query/prompt-rules`、`POST /prompt-rules/{id}/reset`
  （内置规则只能停用/改文案/恢复默认，不能删除）。
- 界面：问数设置 → **生成规则**（列表 + 启停 + 编辑 + 恢复默认 + 新增/删除）。
- 作用域：每条规则可选「全部 / 仅指定数据源 / 仅指定方言」，运行时按当前数据源与方言过滤；
  界面上有「**预览生效规则**」，直接看到这一刻真正拼进提示词的文本（避免"改了但没生效"的错觉）。
- A/B：规则弹窗里可勾选若干条「本轮禁用」并启动一轮评测（`filter.rules_disable`）。
  禁用只作用于**该次运行**（ContextVar），不改库、不影响真实用户；评测指纹
  （`ai_query_testrun.config.fingerprint.rules`）记录规则快照哈希 + 本轮禁用清单，
  跑完在「问数评测 → 报告 → 对比运行」里对比两轮即可看到逐题翻转与准确率变化。
- 边界（重要）：
  1. **核心安全约束**（只读 SELECT / 必须 FROM / 只用给定表）留在 `dialect.CORE_RULES`，只读展示、不可关闭；
  2. **确定性口径**（软删、时间、权限）继续由代码改写，不进提示词；
  3. 表里只放**书写偏好**（别名、格式、占比写法、Top-N 空值）。
- 顺带修掉一处真实不一致：流式路径（`ask_stream`）过去只抄了 (1)~(6)，
  **从来没有** (7) 明细/汇总 与 (8) Top-N 空值 → 同一问题走流式/非流式口径不同。现在两条路径共用一份规则。
