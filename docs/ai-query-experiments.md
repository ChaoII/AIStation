# 问数调参账本（A/B 结论与噪声）

> 为什么要有这个文件：78 题的**同配置重跑**本身就会翻 1~4 题（实测），
> 单跑一次得到的"准确率提升 2 个点"大多数是噪声。凡是写进这里的结论，
> 都必须是**配对重跑 + 内部翻转率**对照过的；落在噪声里的，直接写"没结论"。

## 方法

- 工具：`backend/scripts/eval_paired_variance.py`
- 命令形态：`--configs "baseline,<开关>=<值>" --repeats 3 --dataset fuel-v2`
- 判定：
  1. 每个配置跑 N 次，先看**内部翻转率**（同一题在自己几次之间对错不一致的数）——这就是噪声带；
  2. 再按逐题多数票比两个配置；
  3. `|Δ|` 落在噪声带内 → **不归因给配置**，不改默认值。
- 每一轮开始前清 SQL 缓存；评测走 `bypass_caches()`，召回/prompt 缓存不参与。

## 结论汇总

| 开关 | 默认 | 结论 | 依据 |
|---|---|---|---|
| `schema_column_prune_enabled`（列裁剪） | **开** | 收益明确 | prompt 20,991→10,077 字符（−52%），单轮 475/382s→361/345s（−20%），准确率持平略升（差异在噪声内） |
| `literal_fix_enabled`（字面量等价纠错） | **开** | 收益明确（确定性） | `'烟煤 '` 0 行 → `'烟煤'` 1 行；只做 strip/全角→半角/ASCII 大小写三种等价归一 |
| `schema_asset_meta_enabled`（资产描述注入 prompt） | 关 | **零收益** | 三次实测准确率无变化 → 只保留代码分支 |
| `schema_ont_prop_notes_enabled`（本体属性说明注入） | 关 | **零收益** | 本体属性名与数据源列注释 80/86 完全相同，注入等于写两遍 |
| `enum_hint_enabled`（枚举取值提示） | 关 | **零收益** | 0.9231 → 0.9487（2 题），但配对重跑后落在噪声内，撤回结论 |
| `agno_semantic_enabled`（语义开关） | 开 | **无结论** | 单跑 0.8930 vs 0.8889 方向相反，判定噪声，不改默认 |
| `recall_top_k`（召回表数量） | 12 | **无收益，保持 12** | 见下方 2026-11-04 |

## 2026-11-04：`recall_top_k=6` vs 12

```
baseline        acc=[0.9487, 0.9359, 0.9487]  mean=0.9444  内部翻转 1/78
recall_top_k=6  acc=[0.9487, 0.9487, 0.9231]  mean=0.9402  内部翻转 3/78

逐题多数票：0.9359 vs 0.9487（Δ=-0.0128）  变好 0 题、变差 1 题
变差的那道：每日出入库报表一共有多少条记录？
```

结论：**没有收益，方向还略负**（1 题），且内部翻转从 1 升到 3 —— 更多表被裁掉后
模型选表更不稳定。保持 12，不调默认。

### 这次实验差点测不出东西（重要教训）

做这轮实验前发现：`_RETRIEVAL_CACHE`（TTL 600s）存的是**已按 `recall_top_k` 截断**的
列表，`_SCHEMA_CTX_CACHE`（TTL 120s）存的是**按开关拼出来的 prompt**，而两者 key
都只有「数据源|问题」。也就是说：把 top_k 从 12 改成 6，10 分钟内拿到的还是 12 张表的
旧结果 —— 实验会得出"调了没变化"。

已在 `c9678b7b` 修复：两个缓存的 key 都追加 `_cfg_sig()`（19 个影响召回/prompt 的
开关算短哈希）。**新增任何影响 prompt 的开关，必须加进 `_CTX_CFG_KEYS`**，
否则同类问题会以"偶发、复现不了"的形态再次出现（`tests/test_query_settings_wiring.py`
里有守护用例）。

## 2026-11-04：剩余 6 道失败逐题归因（acc 0.9231 那一次）

不要用"口径差异"一句话糊过去，逐题看 SQL 才分得清是**我们代码**、**金标**还是**模型理解**。

| 题 | 实得 | 金标 | 归因 |
|---|---|---|---|
| 入厂煤批次里矿点名称为空的有多少条 | 255 | 200 | **模型**：少了 `"ISDELETED" = false`，把软删的 55 条算进来了 |
| 矿点名称非空占比 | 7.94 | 9.91 | **模型**：同上，分母含软删行 |
| 每个供应商平均关联几个矿点 | 53 行明细 | 2.64 | **模型**：问句有"平均"，仍按"分组列出"作答，没套 `AVG` |
| 关联最多的那家供应商，占全部关系多少 | 53 行 | 1 行 | **模型**：漏了 `ORDER BY ... DESC LIMIT 1`（问句是"最多的那家"） |
| 按矿点名称统计不同供应商数，并列按名称升序取前 3 | 按名称排的前 3 | 按供应商数倒序、再按名称 | **模型**：多键排序只用了第二键 |
| 每日出入库报表一共有多少条记录 | 无 SQL | 3760 | **我们的代码**：对象路径返回"有行无列"，旧判据放行 → 已修为只看列（`not cols` 即降级） |

结论：**5/6 是模型理解问题，不是口径分歧**；其中 2 道同源（软删除过滤）。

### 待决策（没有擅自改）

1. **软删除过滤**：两套做法各有利弊 —
   - 提示词加规则（"业务表有 `ISDELETED` 列时默认排除，问句本身问已删除时除外"）：
     影响所有题，需 A/B；会多占几十个 token。
   - 生成后 SQL 重写（代码规则）：确定性、零 token、可单测；但属于"替模型做业务判断"，
     误伤风险更高（例如本就该统计全量含删的题）。
   未做：两种都要先量。当前记录在案，避免"下次又当新问题重新发现"。

2. **多键排序 / 取单个**：可考虑在提示词的"查询口径规范"里补一两句
   （`ORDER BY` 多键要按问句顺序、含"最多/第一/那家"必须 `LIMIT 1`）。
   同样需要 A/B，不能凭感觉加。

## 教训清单

1. **噪声带先量，再谈差**。78 题同配置重跑翻 1~4 题；任何 <3 个点的结论都要配对验证。
2. **"改了没生效"要怀疑缓存**，不只是怀疑逻辑。缓存 key 缺维度 = 实验结论作废。
3. **金标要能跑出数据**。停用过 35 道"结算表全空"的旧题（`RAILLOST` 全表合计为 0）。
4. **口径差异不要靠放宽金标"修"**。ID 分组 vs 名称分组这类差异要记进账本，
   而不是把金标改成迁就模型。
