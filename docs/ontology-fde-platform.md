# 本体驱动 + FDE 平台蓝图（Palantir Foundry 式）

> 目标：把 AIStation 从「AI 平台」升级为「本体驱动的数据/决策平台」，给 ERP / CRM / MES 等
> 业务系统**赋能**（消费业务语义，而非每次靠人翻译）。参考 Palantir Foundry 的 Ontology / AIP / FDE。

---

## 一、调研结论：Palantir Foundry 核心

| 概念 | 说明 |
|------|------|
| **Ontology** | 位于原始数据之上的**语义层**，把表/数据集抽象为**带类型的、连通的业务对象**（Patients/Orders/Contracts…）。是 AIP 一切 AI 功能、Copilot 动作、Workshop 应用的读写基座。 |
| **Object Type** | 业务实体的 schema：主键、类型化属性、显示名、图标/颜色，backed by 数据集。 |
| **Link Type** | 对象间的类型化关系（1:N / M:N / 自引用）。 |
| **Action** | **带类型、可审计**的变更操作（创建/修改/删除对象），执行前校验规则，是治理与合规的落点。 |
| **OSDK** | TS/Python 客户端：查询对象、遍历 Link、执行 Action，供外部应用/Agent 消费。 |
| **AIP grounding** | 问「订单#12345 状态」时，AIP 自动取 Order 对象作为** grounded context** 喂给 LLM，杜绝幻觉。这是 Palantir 的护城河：**AI 拿到实时企业语义**。 |
| **FDE** | 前线部署工程师（业务翻译官/数据本体工程师/应用交付工程师）按命题配置，走「驻场诊断→建模→组装→影子运行→移交沉淀」。 |

**最重要的两点**：
1. **本体是「写」与「读」的统一基座**：应用/AI 都从本体拿对象、写回走 Action（审计）。
2. **AI 的 grounding** 是本体产生的直接商业价值，不是「文档」。

## 二、AIStation 现状 vs Palantir（对照）

| Palantir 能力 | AIStation 已有 | 状态 | 要补 |
|---------------|---------------|------|------|
| Object Type | 数据资产（表）+ 概念（本体）+ 模型/工具/Agent | 🟡 有雏形 | 对象化（主键/属性/显示名）+ 覆盖业务系统对象 |
| Link Type | 字段关联推断 + 知识图谱（AGE 边：包含/关联/映射/同域/概念） | 🟡 有 | 语义更强的 Link（1:N/M:N/自引用）+ 业务对象间关系 |
| Action | 无（只有提案 propose_*） | 🔴 缺 | **类型化 Action**（写回业务系统 + 校验 + 审计留痕） |
| OSDK | 问数工具 / Agent 工具 | 🟡 部分 | 统一对象查询/遍历/写回 SDK（供 Agent/应用/工作流消费） |
| AIP grounding | 问数搜索 + 语义 schema 注入 + 知识库 RAG | 🟡 有 | **按业务问题自动取对象**喂给模型（question→对象→上下文） |
| 知识图谱 | Apache AGE（表/字段/指标/术语/域/概念，Cypher 跨域） | ✅ 强 | 扩充业务对象节点 + Action/血缘 |
| NL2SQL | 12 工具 + 本体黑话 + 93 条基准 93% | ✅ 强 | 成为「本体查询」的一种出口 |
| 元数据治理 | 数据资产（描述/业务域/业务场景/关联/敏感/画像） | ✅ 强 | 版本/血缘/权威等级/责任人/生命周期 |
| FDE 交付 | 无 | 🔴 缺 | 命题→诊断→建模→组装→影子→移交的**交付工作台 + 留痕** |

**结论**：AIStation 的「语义/本体」和「查询/检索」底子已经很接近 Palantir 的 Ontology + AIP，**最缺的是三块**：
1. **Action（写回 + 审计）** —— 让本体不只是「读」的，而是能安全写回业务系统的。
2. **企业语义对象的「对象化 + 建模工作台」** —— 把 ERP/CRM/MES 的实体建成 Object/Link。
3. **FDE 交付闭环（命题→留痕→复用）** —— 让每次交付沉淀为资产，不是房租。

## 三、三层架构映射到 AIStation

| 层 | Palantir | AIStation 落点 |
|----|----------|----------------|
| **交付闭环层**（业务命题怎么进出） | 命题→诊断→建模→组装→影子→移交 | 新增「**交付工作台**」（命题管理/五步单/影子运行/移交清单） |
| **企业语义层**（企业被机器理解成什么） | Ontology（Object/Link/Action） | 强化「**本体中心**」：对象/关系/属性/约束/事件/流程/规则/服务 + 权限/血缘 |
| **平台工程层**（语义怎么稳定跑/安全改） | 管道/编排/权限/版本 | 已有数据管道/Agent 编排/权限；**补版本管理/回滚/审计日志/影响分析** |

**三条接缝（决定架构是否成立）**：
- **语义上下文**：任务下发强制绑定「本体版本号 / 规则版本 / 权限策略版本 / 数据快照」。
- **底座支撑**：本体资产以**可执行对象**存储（数据契约 + 工具接口），文档自动生成但**不能只有文档**。
- **交付留痕**：交付单强制关联本体资产 ID，未留痕不得验收。

## 四、与 ERP/CRM/MES 结合的路径（赋能业务系统）

1. **连接器/数据管道**：通过 API / DB 连接器 / 消息流把 ERP(订单/库存)、CRM(客户/商机)、MES(工单/设备/批次) 拉入。
2. **语义抽取与消歧**：同名异义/异名同义对齐（如三套系统三个「客户」定义 → 统一为服务端客户对象 + 各系统别名映射）。
3. **对象化**：建成 Object Type（客户/订单/工单/设备/批次/BOM）+ Link Type（订单-行项、工单-设备、批次-原料）。
4. **规则/约束注入**：单位量纲、班次日历、状态机、GMP/ISO 合规约束进本体，组装不越线。
5. **AI/应用消费**：Agent/看板/工作流从本体取对象（grounded），不各自硬编码。
6. **写回（Action）**：审核通过的操作经 Action 写回业务系统，全程留痕。

---

## 五、FDE 五步交付（方法论文案落地）

- **① 驻场诊断**：蹲现场、访谈、跑数据 → 产出「**本体缺口清单** + 验收指标 + 数据质量/合规评估」，不是传统需求文档。
- **② 本体建模**：针对缺口补建 Object/Link/约束/规则 → **复利核心入口**。
- **③ 应用组装**：基于本体定义组装看板/Agent/工作流（语义已对齐，不再反复问字段含义）。
- **④ 影子运行**：新旧并行、口径对齐、与黄金标准一致、差异可解释并回溯到本体。
- **⑤ 移交沉淀**：SOP/培训/定责任人 + **新建/修改的本体对象写回本体库并关联交付记录**（走提案→评审→发布→兼容检查→弃用策略）。

**度量**：交付效率（交付周期/返工率/**本体复用率**）+ 质量合规（语义冲突数/Agent 准确率/审计覆盖率）。

## 六、落地路线图（建议）

### P0（先做，撬动最大杠杆）
1. **「本体中心」对象化**：把数据资产 + 概念升级为 **Object Type**（主键/属性/显示名/图标），**Link Type** 可选择 1:N/M:N/自引用；供应商/客户/工单/设备/批次等业务对象建模 UI。
2. **对象查询 SDK 化**（给 Agent/问数/工作流统一消费）：`getObject(订单#12345)` → 自动取该对象及邻居作为 **grounded context** 注入模型（对标 AIP grounding）。
3. **交付工作台**：命题管理 + 五步单 + 本体缺口清单 + 交付留痕（强制关联本体资产 ID）。

### P1
4. **Action（写回 + 审计）**：类型化 Action，校验规则 + 审计日志 + 审批，写回业务系统。
5. **本体版本 / 血缘 / 影响分析 / 回滚**；权威等级 / 责任人 / 生命周期（草案→试行→发布→弃用）。
6. **连接器**：ERP/CRM/MES 连接器 + 语义抽取/消歧管道。

### P2
7. **影子运行/黄金标准比对**；行业本体复用（ISA-95/IEC 62264、OPC UA、ISO 15926、ISO 9001、GMP）。
8. **FDE 人才模型**：业务翻译官/数据本体工程师/应用交付工程师按命题配置。

## 七、边界与轻量取舍

- **什么时候用重本体**：多系统、语义冲突多、口径波动、权限/血缘复杂、AI/Agent 直接消费、交付频次高 → **本体值得**。
- **什么时候轻量更划算**：单系统、语义稳定、以文档+看板为主、无 AI 直接调用 → 先把**文档/数据字典/ER图/SQL注释/SOP**做齐（必要不充分），不要一上来就上重本体。
- **判断一次交付是「资产」还是「房租」**：下一命题来临时，能否直接从本体库取现成对象/规则**组装**而非重新蹲现场；出问题能否**定位到具体本体/规则/审批版本并回滚**；平台管道/编排/权限/版本能否稳定支撑，不改一个字段全线崩。

---

## 八、结论

AIStation 已经是「有本体的 AI 平台」的雏形（语义层 + 知识图谱 + NL2SQL + 知识库 + Agent + 工作流 + 数据资产治理）。要成为 Palantir 式的「本体驱动数据/决策平台」并给 ERP/CRM/MES 赋能，**核心是补三块**：**① 对象化建模工作台（Object/Link）② Action 写回与审计 ③ FDE 交付闭环（命题→留痕→复用）**。抓住这三块，平台就从「AI 能力平台」变成「企业业务的语义基座 + 决策中枢」。
