# 本体（Ontology）使用说明

> 面向使用者的操作手册。核心一句话：**本体是「业务对象 + 关系 + 可执行能力」的登记处，Agent 从这里装配工具。**

页面位置：`AI 管理 → 本体`（`/ai/ontology`）

---

## 一、五个概念是什么

| 概念 | 含义 | 数据存在哪 |
|------|------|-----------|
| **本体** | 对象类型的顶层容器，比如「数据表本体」「业务本体」 | `ai_ont_domain` |
| **对象类型** | 一个业务对象，如「摄像机表」（`video_cameras`）。由表结构导入，也可手建 | `ai_ont_object` |
| **属性** | 对象的字段，如「摄像机名称」「设备类型」。带类型与枚举 | `ai_ont_property` |
| **关联 Link** | 对象之间的业务关系，如 告警记录 →（摄像机） | `ai_ont_link` |
| **动作 Action** | 对对象的一次**写回**，带字段白名单与审批门禁 | `ai_ont_action` |
| **函数 Function** | 挂在对象上的**纯算术计算器**，供问数/Agent 复用 | `ai_ont_function` |

另外两个是自动产生的：**变更记录**（谁在什么时候改了什么）、**版本**（对象定义的快照，可对比可回滚）。

## 三、页面结构：左树 → 右页签 → 抽屉

```
┌────────────────────┬────────────────────────────────────────────────┐
│ 本体          [+]  │ 数据表本体 对象83 关系33 动作7 函数10 [维护▾][编辑本体]│
│ [搜索]             ├────────────────────────────────────────────────┤
│ ▾ 全部本体 (83)    │  对象类型│关系类型│本体可视化│图谱│导入本体│…   │
│ ▾ 数据表本体 (83)  ├────────────────────────────────────────────────┤
│ ▸ 业务本体 (0)     │  内容区（该本体 × 该视图），自己滚动            │
└────────────────────┴────────────────────────────────────────────────┘
        点表格某行 → 右侧滑出「对象详情抽屉」（属性/关联/动作/函数/变更记录/版本）
```

- **左树只放本体**（可建很多个）。选中哪个本体，右侧所有页签就都收窄到它
- **右侧恒定为 8 个页签**：对象类型 · 关系类型 · 本体可视化 · 图谱 · 导入本体 · 深度分析 · 变更记录 · 版本
- **对象详情走抽屉**，不再往页签里再套一层页签
- **右上角「维护」下拉**是全局维护入口，任何页签下都能点到：
  | 菜单项 | 作用 |
  |--------|------|
  | 业务语义回填 | 注释→对象/属性名与枚举、真实外键→关系（幂等） |
  | 写入示例能力 | 10 个函数 + 7 个对象动作（按编码判重） |
  | 批量归属本体（已选 N） | 把「对象类型」页签里勾选的对象挪到别的本体 |
  | 待审批的版本发布（N） | 查看并批准待审批的版本快照 |

选「全部本体」= 跨全部本体，页签与单个本体时完全一致，只是范围不同。

## 四、怎么用：八个视图逐个说

以「摄像机表」为例：左树选「数据表本体」→ 右侧「对象类型」页签 → 点表格里的「摄像机表」那一行 → 抽屉打开。

### 对象类型
该本体下的对象清单：名称（业务名）· 编码 · 描述 · 属性数 · 关联数 · 动作数 · 函数数 · DQ 分。
- 点行 → 抽屉看详情；右侧「详情 / 物化为表 / 删」
- 顶部「+ 新建对象」手建一个（可按「所属本体」归类）
- **勾选左侧多选框**可批量操作：顶部「归入本体（N）」把选中的对象一次性挪到别的本体（不选目标 = 退回未分组）
- **DQ 分是按钮**：点它看该对象的健康分 / 完整性 / 唯一性 / 新鲜度与具体质量问题

### 关系类型
该本体内所有关系：关系名 · 源对象 · 源字段 · 目标对象 · 目标字段 · 基数。
**这些关系来自数据库真实外键**，不是手填的。「全部本体」下是 33 条。

### 本体可视化
对象 + 关系的关系图（元模型视图）。点节点可直接跳到该对象的抽屉。

### 图谱
**数据资产统一图谱**，与上面那个是两回事：这张图画的是 表 / 字段 / 指标 / 术语 / 概念 五类节点，以及 `has_field`、`related_to`、`uses_table`、`maps_to`、`subconcept_of` 五类边。
- 顶部可按节点类型勾选过滤，默认收起「字段」（数量最多、属实现细节）
- 点「刷新」重新拉取

### 导入本体
- **从数据源导入表结构**：选数据源 → 「批量导入本体对象」。默认排除 `alembic_version`、`apscheduler_jobs`、各类日志与关联表等无业务语义的表；勾「包含纯技术表」则全量导入
  - 数据源下拉里带「已同步 N 张表」，**默认自动选中已同步表最多的那个**；若为 0 张，导入按钮会禁用并提示先去同步
  - 导入是**幂等**的，可重复执行
- **应用行业本体模板**：内置 3 个 —— 制造业（ISA-95/IEC 62264）、制药（GMP/ICH）、通用业务。点「应用」预建标准概念
- **维护本体**：两个一键按钮（详见第六节）

### 深度分析
本体建模分析：关系完备性 · 关系密度 · 连通分量 · 孤立对象 · 缺主键对象 · 中心度 Top · 建模建议。

### 变更记录
本本体内对象的定义变更留痕（对象/属性/关系/动作/函数的增删改，含操作人）。「全部本体」下当前 37 条。

### 版本
对象定义的快照。顶部选一个对象 → 「发布版本」快照当前定义；列表里可「对比」（新增/删除/变更属性）与「回滚」。

- 超管发布**直接生效**；非超管发布会转成**待审批单**，由超管在右上角「维护 → 待审批的版本发布」里批准

### 抽屉里的六个页签（对象级）

#### 1. 属性
对象的字段。中文名来自数据库列注释；`设备类型`、`码流类型` 这类注释里列了候选值的，已自动解析成 **enum**（「枚举/来源」列可见）。
- 新增属性：点「+ 新增属性」
- 「敏感」计数 > 0 时在抽屉标题行标红，配合字段级 ACL 用

#### 2. 关联 Link
看这个对象和谁有关系。摄像机表有 6 条：告警记录、告警规则、算法任务、录像文件、录像计划都指向它，它自己指向「摄像机分组」。
- 关系名是业务名词（「摄像机」「摄像机分组」），不是表名
- 基数 `many_to_one` 来自「该外键列是否唯一」的实际判断
- 新增关联：点「+ 新增关联」，选源对象/目标对象/基数

**这些关系是从数据库真实外键自动生成的**，不是编的。数据源表结构变了，重跑回填即可。

### 3. 动作 Action
这里是**能真正写回数据库的操作**，一行一个：动作名 / 编码 / 写回目标 / 方式 / 可写字段 / 是否需审批。

摄像机表有 2 个（`cam_rename` 改名、`cam_mark_offline` 标记离线）；告警记录表有「确认告警」「标记告警误报（需审批）」等。合计 7 个。

**怎么执行（界面上）**：每行右侧点绿色「执行」→ 弹窗里填「对象行 ID」（目标表主键）+ 要写的字段。
- 字段输入框是**按动作定义动态生成的**：优先用 `input_schema`（带中文标签），没有则退回可写字段列表
- 勾了审批的动作，弹窗顶部会提示；不勾「已获审批」只会生成待审批单，**不会写库**
- 执行结果（成功 / 需审批 / 被白名单拒绝 / 报错）直接显示在弹窗里

**接口等价形式**：`POST /api/v1/ai/ontology/action/execute`

```json
{ "code": "cam_rename", "object_key": "12", "params": { "name": "东门-1号" } }
```

执行链路上的三道闸：
1. **白名单**：`params` 里的字段必须在动作的可写白名单内，否则直接拒绝
2. **审批门禁**：动作勾了「审批」时，不带 `approve=true` 只会落一张**待审批单**（进 `ai_action_log`，审批中心可见），不写库
3. **审计**：成功/无匹配都写 `ai_action_log`

> 目前只支持 `update` 写回；`insert` / `delete` 会被拒绝。

### 4. 函数 Function
**注意：函数是纯算术计算器，不是 SQL 查询。**

它的表达式由调用方**传入数值参数**后求值，支持 `+ - * /`、比较、布尔，**不支持函数调用和字段访问**。例如：

| 函数 | 表达式 | 调用 |
|------|--------|------|
| 摄像机在线率（%） | `online_count / total_count * 100` | 传 `online_count=93, total_count=120` → `77.5` |
| 告警抑制窗口（分钟） | `interval_seconds / 60` | 传 `interval_seconds=300` → `5.0` |
| 训练预计剩余（小时） | `elapsed_hours * (100 - progress) / progress` | 传 `elapsed_hours=2.5, progress=40` → `3.75` |

所以**写函数时 expr 里只能出现参数名和数字**；参数含义写在「说明」里，Agent 会读到。

> 为什么不用 SQL？因为本体函数的定位是「Agent 手里已有的数值做一次业务换算」。要查库请用问数工具。

### 5. 变更记录 / 版本
- **变更记录**：对象/属性/关联/动作/函数的每次增删改都有留痕，含操作人。出问题时先看这里。
- **版本**：点「发布版本」把对象当前定义（对象+属性+Link+Action+函数）快照成 v1、v2…；列表里可「对比」（新增/删除/变更属性）与「回滚」。

## 五、和 Agent 接线（重点）

**接线方式：把本体函数/动作的编码填进智能体的 `capabilities` 字段。** 界面上就是：

`AI 管理 → 智能体 → 编辑 → 本体工具（函数 / 对象动作）` → 下拉里勾选 → 保存。

勾选即授予：运行时 Agent 会把每个编码装配成一个可调用工具。

- 命名规则：函数 → `ont_fn__<code>`，动作 → `ont_action__<code>`
- 动作被调用时不是直接写库，而是返回一个**待确认载荷**（`api: ontologyAction`），由前端/调用方决定是否执行；真正写库仍走第三节的三道闸
- 此外 Agent 始终带一个 `list_ontology` 接地工具，让它知道本体现在有哪些对象和能力

### 工具描述由本体决定（P2）

动作与函数都有一等字段 **`Tool description`**（在动作类型视图的元数据区、函数编辑弹窗里都能写）：

| 情况 | Agent 看到的工具描述 |
|------|-------------------|
| 填了 `Tool description` | 直接用它（**推荐**：写清"这个动作做什么、什么时候该调用"） |
| 没填 | 回退到普通「描述」 |
| 都没填 | 回退到结构化摘要（对象动作：名称 + 写回目标.方式） |

### 入参 schema 由本体决定（P2）

在动作/函数上声明 **参数**（key / 显示名 / 类型 / 是否必填 / 说明 / 可选值），会**直接生成 Agent 工具的入参 JSON Schema**——不需要另外写工具定义。

- 动作：优先用 `参数` 声明 → 回退 `input_schema` → 回退可写字段白名单；update 类动作会自动补上必填的 `object_key`（目标行主键）
- 函数：优先用 `参数` 声明 → 回退从表达式里推断变量（推断出的都当数值）

**界面上有校验**：函数表达式里用到的变量必须都在参数中声明，否则保存被拦下——避免 Agent 拿到一个传不进值的工具。

### 调用前预校验（P2）

Agent 调用动作时，**在写库之前**就会检查：

1. 字段是否都在可写白名单内（不在则拒绝，并列出可写字段）
2. 必填参数是否齐全
3. update 类动作是否给了目标行主键

把原先的运行期失败提前成可读错误。

### 可查范围（P2）

`visibility = hidden` 或 `status = deprecated` 的对象类型 / 动作 / 函数，**不会暴露给 Agent**：既不生成工具，也不出现在能力清单里。即便被勾选也不生效。

### 依赖可追溯（P2）

对象类型 Overview 的 **「依赖」分区**会列出引用它的智能体及命中的能力编码（如 `问数助手（cam_online_rate）`）。改本体前先看这里，能知道会影响哪些智能体。

> 顺带修了一个阻塞缺陷：`capabilities` 此前只在数据库里有列，模型与接口 schema 都没声明，导致**前端勾了也存不进、运行时也读不到**——整条接线在第一步就是断的。现已贯通。

**当前已接线**：智能体「问数助手」已接入 5 个**只读**函数（在线率、告警确认率、告警响应时长、指标提升幅度、录像占用）。未接任何写回动作——需要时在界面上自行勾选。

## 五之二、工作副本：改动先入草稿，保存才落库（P3）

**这是使用本体的方式上最重要的一个变化**：以前点「保存」立即写库，现在所有改动先进**工作副本**，点右上角「保存」才真正落库。

### 怎么看

- 头部会出现 **「保存」按钮 + 未保存数量角标**（如 `1`）和一个 **「丢弃」** 按钮，只有存在未保存改动时才出现
- 界面上**立刻能看到改动效果**（列表里就是新名字、新属性），但**数据库里没有变**——这是有意设计的
- 点「保存」→ 弹出**审核面板**：

| 分区 | 含义 | 是否会阻止保存 |
|------|------|--------------|
| **错误** | 缺必填项、编码重复、关系方向不合法、函数表达式变量未声明等 | **会阻止** |
| **警告** | 没填描述/API 名/写回目标、未配白名单、关系端点对象不存在等 | **不会阻止**，仅提示 |
| **破坏性改动** | 删除、恢复历史版本、改主键属性、改属性类型 | 需**输入实体名称**才能确认 |

- 点「丢弃」→ 二次确认后清空全部草稿，数据库不受影响

### 哪些操作会入草稿

对象类型 / 属性 / 关系类型 / 动作类型 / 函数的**新建、修改、删除**，以及**从历史版本恢复**——全部先入草稿。

### 历史与恢复

「历史」页列出**版本快照**（带发布时间）和**变更留痕**。点某个版本的「恢复」→ 该恢复动作会作为一条草稿进入待保存列表，点「保存」后才真正覆盖当前定义。

### 导入 / 导出

「导入导出」页：

- **导出**：把当前本体的定义（对象类型/属性/关系/动作/函数，**不含数据行**）下载成 JSON
- **导入到待保存列表**（推荐）：导入内容先进草稿，可以逐条审核后再保存
- **直接导入（跳过审核）**：立即写库，有二次确认

> ⚠️ 官方明确声明「不要依赖导出的 schema」，这里同样只保证**同版本内可导回**，跨版本不保证兼容。

### 用量

「使用量」页（对象类型详情里也有一个）显示三个读数，**全部取自既有日志表，没有额外埋点**：

| 指标 | 来源 |
|------|------|
| 读数 | Agent 工具调用次数（`ont_fn__*` / `ont_action__*` / `list_ontology`） |
| 写入 | 动作执行次数 |
| 交互 | 本体定义改动次数 |

官方的「活跃用户数」需要按用户聚合调用日志，**本版未做**。

### 清理

「清理」页按现有定义派生出弃用/删除候选（不做假数据）：

- 没有任何属性 → 无法承载数据（高）
- 既无关系也无动作/函数 → 疑似孤岛（中）
- 已标记 deprecated → 可考虑删除（低）

可以一键「标记弃用」（同样入草稿）。

## 五之三、实例层：对象探索 / 对象视图 / 实例图 / 写回（P4）

前面几节讲的都是**类型层**（对象类型、关系类型的定义）。本节是**实例层**——真实数据行。

> **一句话区分**：类型层是「摄像机表这个对象类型长什么样」，实例层是「东门那台摄像机的实时状态」。

### 对象探索

「对象探索」页：

1. 顶部选一个**对象类型**（只列出已物化、有支撑表的）
2. 输入关键词搜索（在标题属性上模糊匹配），或直接浏览
3. 表格显示真实数据行；**勾选多行**可以做批量操作

### 对象视图（单实例）

点某行的「视图」，右侧抽屉展开：

| 分区 | 内容 |
|------|------|
| 属性 | 该实例的全部属性值；**敏感字段显示为 `••••••`** |
| 编辑属性（Writeback） | 仅在对象类型开启「可编辑」时出现，可直接改属性值 |
| 关系跳转（Search Around） | 该对象类型参与的所有关系，可一键跳到关联实例 |
| 可执行动作 | 该对象类型下的动作，点一下就能对这个实例执行 |

### 关系跳转（Pivot / Search Around）

关系是**有方向**的，跳转会**双向**处理：

- 摄像机 → 摄像机分组：走 `video_cameras.group_id`（正向）
- 摄像机 → 告警记录：走 `video_alarm_records.camera_id`（**反向**）

点「跳转」后弹出关联实例列表，点「继续」可以换个对象类型继续往下钻。

### 实例图

点某行的「图」，打开**实例层图**：

- **节点 = 真实数据行**，边 = 按关系类型实际连出来的
- 可切换扩展 1/2/3 步（Search Around 多步扩展）
- 可按关系类型过滤
- 点节点会提示它是什么实例

> 别和**类型层图**搞混：类型层图在「关系类型 → 打开某个关系 → 可视化」，画的是对象类型和关系类型的**定义**。两处的说明文字都做了区分。

### 批量执行动作

1. 勾选若干行 → 点「批量执行动作（已选 N）」
2. 在弹出的列表里选一个动作
3. 填参数（参数来自动作的**参数声明**，回退到可写字段白名单）
4. 点「执行」

**仍然走全部门禁**：可写字段白名单校验 → 审批门禁（若动作开启了审批，需要打开「已确认」）→ 每个实例一条审计记录。

> 批量是**逐个串行**执行的：部分成功是可能的，失败的会在提示里列出。

### Writeback（属性写回）

**默认关闭**。开启方式：对象类型 → 元数据区 → 打开「可编辑（Writeback）」。

开启后，对象视图里会出现「编辑属性」表单，改完点「保存修改」直接写真实数据表，并留痕。

**写回的三条限制**：

1. 对象类型必须开启可编辑
2. 只能写**本体里声明过**、且**不是**「仅动作填充（edit_only）」、**不是**敏感的属性
3. **字段名像敏感信息的一律拒绝**，即便本体里没勾敏感：
   `password / passwd / pwd / secret / token / api_key / private_key / credential / salt / signature / access_key / session_id`

第 3 条是兜底防线——实测发现 1479 个属性里 `sensitive` 标记**一个都没勾**，只靠人工勾选是不够的。现在「业务语义回填」会自动把这类属性标记为敏感。

### 资产图谱（数据血缘）不是本体图

「AI 管理 → 资产 → 图谱」画的是**数据侧血缘**（数据库表 / 字段 / 指标 / 术语 / 概念），由 schema 同步与知识库抽取而来。它和本体**类型层图**不是一回事，界面上已加说明区分。

## 五之四、高级类型系统（P5）

### 对象类型组（「高级类型」页 → 对象类型组）

**跨对象类型**的多对多分组。注意和「所属本体」的区别：

| | 所属本体（domain） | 对象类型组（group） |
|---|---|---|
| 关系 | 一个对象类型**只能属于一个** | 一个对象类型**可以属于多个** |
| 用途 | 划分业务域 | 跨域打标签、批量筛选 |

界面上可以勾选组成员，删除组前会显示引用方。

### 值类型（「高级类型」页 → 值类型）

基础类型之上的**语义包装**，例如「邮箱地址」= string + 正则约束。

可设的约束：`pattern`（正则）、`min`/`max`（数值范围）、`min_length`/`max_length`（长度）、`options`（枚举取值）。

- 值类型带**版本**：每次改定义自动 `version + 1`
- 可以设**权限角色**（当前仅存储，实例层读写尚未按角色过滤）
- **被引用时无法删除**，会列出引用方

### 共享属性（左侧导航「共享属性」）

**定义一次、多个对象类型引用**。关键点：**只共享元数据，不共享数据**——每个引用它的对象类型仍然用自己表里的列存值。

- 改共享属性的类型 / base type / 值类型 → **自动同步**到所有引用方
- 被引用时无法删除
- 在对象类型 → 属性 → 新建属性时，把「类型类别」选成「共享属性」，再选共享定义即可

### Struct

属性的一种类型类别：结构体，由**单个 struct 列**支撑。在属性弹窗里把「类型类别」选成 `Struct`，然后用 JSON 描述它的字段组成。

> 当前 `struct_fields` **只存储、不参与读写**（真实数据仍按单列处理）。

### 接口（左侧导航「接口」）

接口声明**必需属性 / 必需关系 / 必需动作**，对象类型可以实现它。

**约束在实现侧强制**：在接口弹窗里勾选实现者时，不满足要求的对象类型**会被拒绝并列出具体缺项**，例如：

```
已让 0 个对象类型实现该接口，1 个不满足约束被拒绝
被拒：告警记录表（动作：修改摄像机名称）
```

「合规检查」按钮会扫描所有已登记的实现在改完接口后是否掉队。

> 当前只校验**同名项是否存在**，不校验关系另一端的接口类型是否匹配。

### 派生属性

属性的「类型类别」选成「派生属性」后，可以**经关系链聚合出**一个值。配置形如：

```json
{"source_object":"video_alarm_records","link_path":[27],"aggregation":"count","limit":10}
```

| 配置 | 说明 |
|------|------|
| `source_object` | 关系链走到的目标对象类型（**提供值的那一侧**） |
| `link_path` | 关系 ID 列表，从当前对象类型出发 |
| `aggregation` | 9 种之一：`count` / `sum` / `avg` / `min` / `max` / `first` / `last` / `collect_list` / `collect_set` |
| `property` | 要聚合的属性（`count` 可省） |
| `limit` | collection limit，**默认 10、最大 100** |

**三条硬限制**（界面上也有提示）：

1. 关系链**最多 3 层**
2. collection limit **1–100**
3. **派生属性不能依赖另一个派生属性**

配置好之后可以在弹窗里**试算**（填一个实例主键，立刻看到结果与匹配条数）。

> 计算是**实时遍历**真实数据，没有物化缓存——数据量大时会慢。

## 五之五、动作的三件事：提交条件 / 规则 / 副作用（P0 修复）

> **修复前的状况**：这三个字段在界面上能填、库里也存了，但**执行时完全不生效**——
> 「规则」页显示的还是一张从 `method`+白名单推导出来的假表。P0 把它们做成了真的，
> 并加了「试运行」让你在写库前就能看到会发生什么。

### 执行顺序（七道闸）

```
① 提交条件 → ② 值类型约束 → ③ 规则/白名单 → ④ 审批门禁
→ ⑤ 执行规则 → ⑥ 执行副作用 → ⑦ 审计留痕
```

任何一道不过都会带着**可读的原因**拒绝，并在 `ai_action_log` 里留下 `rejected` 记录。

### ① 提交条件（Submission criteria）

动作类型 → **安全与提交条件** → 「编辑提交条件」。决定**这个动作能不能被提交**。

条件由「取值 + 算子 + 取值」组成，可嵌套 AND/OR/NOT，每条根级条件带**失败信息**（不满足时原样回给调用方）。

| 取值模板 | 含义 |
|---|---|
| `current_user` | 当前提交者的用户 ID |
| `current_user_group` | 当前提交者所属的组/角色（含直接与继承） |
| `parameter` | 动作参数；带 `property` 时可取**对象参数的某个属性**（去真实数据里查） |
| `execution_context` | 执行上下文，目前只有 `is_scenario`（我们没有场景，恒为 false） |

| 算子 | 适用 | 说明 |
|---|---|---|
| `is` / `is_not` | 单值 | 相等 / 不等 |
| `matches` | 单值 | 正则匹配（正则写错时**判为不通过**，不放行） |
| `lt` / `lte` / `gt` / `gte` | 单值 | 数值比较 |
| `is_empty` / `is_not_empty` | 单值 | 空 / 非空 |
| `includes` / `includes_any` / `is_included_in` / `each_is` / `each_is_not` | 多值 | 列表包含关系 |

示例：

```json
[{"operator":"is_not_empty","failure_message":"新名称不能为空",
  "left":{"kind":"parameter","value":"name"}},
 {"operator":"includes","failure_message":"只有管理员角色能改摄像机名称",
  "left":{"kind":"current_user_group"},"right":{"kind":"static","value":"管理员角色"}}]
```

### ② 规则（Rules）

动作类型 → **规则** → 「编辑规则」。决定**这次提交到底写什么**。

支持的规则类型：**修改对象 / 创建对象 / 删除对象**（官方的链接类规则、函数规则、接口规则尚未实现）。

每种规则由若干「赋值」组成，赋值来源有五种：

| 来源 | 写法 | 取值 |
|---|---|---|
| 参数 | `{"property":"name","source":"parameter","value":"name"}` | 取同名参数（或 `value` 指定的参数） |
| 静态值 | `{"property":"kind","source":"static","value":"camera"}` | 固定值 |
| 当前用户 | `{"property":"updated_by","source":"current_user"}` | 提交者 |
| 当前时间 | `{"property":"updated_at","source":"current_time"}` | 提交时刻 |
| 对象参数的属性 | `{"property":"status","source":"object_parameter_property","parameter":"aircraft","object_property":"status"}` | 去真实数据里查该对象参数的某属性 |

> **未配置规则时**走兼容路径：按「写回目标表 + 可写字段白名单」执行 update。

### ③ 副作用（Side effects）

同样在**规则**页编辑。支持两种：

| 类型 | 行为 |
|---|---|
| `notification` | 写站内信（`sys_user_notification`），可指定收件人；标题/内容支持 `{{参数名}}`、`{{当前用户}}`、`{{当前时间}}` |
| `webhook` | 发**真实 HTTP 请求**（POST/PUT/PATCH/GET），可设 `timing`（编辑前/后）、`timeout`、`blocking` |

**阻塞与非阻塞的差别**：`blocking: false`（默认）时请求失败只记录不中断；`blocking: true` 时失败会返回错误——但**编辑已经应用**（与官方"Webhook 可在编辑前后执行"的语义一致）。

Webhook 的 URL 必须是 `http://` 或 `https://`。

### ④ 试运行（Test run）

规则页或安全页的「试运行」按钮：填一组参数 → **不写任何数据**，直接看到

- 每条提交条件逐项判定结果（含左值/右值实际取值）
- 规则会产生哪些编辑（列 → 值）
- 副作用会发什么

> 试运行用的是**你当前正在编辑的配置**（含工作副本里还没保存的改动），
> 而真正执行用的是**已保存的定义**。

### ⑤ 值类型的角色（roles）

值类型上的 `roles` 现在**真正生效**，语义对齐官方`value-types-permissions`：

- 列表里的角色才能把该值类型**分配给属性**（空 = 不限制）——不满足时保存属性会被拒，并告诉你当前实际角色
- **增删改值类型**需要管理员角色（超管或名字含「管理」的角色）

### ⑥ 值类型约束接到了写入路径

动作参数如果声明了值类型（参数 JSON 里的 `value_type`），提交时会按该值类型的
`pattern` / `min` / `max` / `min_length` / `max_length` / `options` 校验，不通过则拒绝（`blocked_by=value_type`）。

> 实例层 Writeback 目前**还没接**值类型校验，这是已知缺口。

## 五之六、函数：四种形态（P2 新增）

> **P2 之前**：函数只是「库内四则运算」，且**存的表达式跑不通也不报错**——
> 例如库里原有的 `avg_amount` 写着 `AVG(amount)`，这种写法其实从来没被求值过。
> P2 把函数做成真正的 **Logic 资产**，并在保存时就校验定义。

### 为什么不建代码沙箱

官方函数是 TypeScript / Python 函数。我们**不引入代码执行沙箱**（安全与运维成本过高，§9 已列为非目标），
改用**声明式函数**：用受控表达式 + 四种形态覆盖同样的用途。

### 四种形态

| 形态 | 用途 | 配置 |
|---|---|---|
| **表达式** | 算术、比较、三元表达式 + 33 个白名单内置函数 | `expr` |
| **关联聚合** | 沿关系链在关联对象上聚合 | `from_object` / `link_path` / `aggregation` / `property` / `limit` |
| **外部服务** | 调外部 REST API | `url` / `method` / `headers` / `body_template` / `result_path` / `timeout` |
| **模型调用** | 调平台已登记的模型 | `model_id`（留空用默认）/ `system` / `prompt` / `temperature` |

### 内置函数（33 个，只能调这些）

```
数值：abs  min  max  round  floor  ceil  sqrt  pow  sum  avg  percent
文本：concat  lower  upper  trim  len  contains  startswith  endswith
      str  int  float  bool
判空：coalesce  iif
日期：now  today  days_between
正则：regex_match  regex_extract
JSON：json_get
集合：any  all
```

> 表达式**没有属性访问、没有任意函数调用**：`a.b` 与 `__import__('os')` 都会被拒。
> 正则写错时条件判为**不通过**（不会意外放行）。

### 入参（inputs）：声明 + 来源 + 类型转换

入参是一个 JSON 数组，每项可声明 `key` / `name` / `type` / `required` / `description` / `source`：

| `source` | 取值来源 |
|---|---|
| `parameter`（默认） | 调用方传进来的参数 |
| `object_property` | **对象上下文**里该属性的值（需填 `object_property`，会自动加载对象实例） |
| `static` | 声明里的 `default` |
| `current_user` | 当前调用者 |
| `current_time` | 当前时间 |

> **类型转换很重要**：界面输入框与 Agent 调用传进来的都是**字符串**。
> 声明 `type: number` 后会自动转成数字，`online / total` 才不会变成 `'8' / '10'` 直接报错。
> **未声明 `type` 时原样透传**——老函数（只写了 `expr`）不受影响。
>
> 老函数没声明入参时，系统按**表达式里的变量**推断为数值型（与 Agent 工具 schema 的既有约定一致），
> 运行弹窗也会据此生成输入框并提示「建议正式声明入参」。

### 出参（outputs）

声明返回值结构（`key` / `name` / `type`），会写进 Agent 工具说明，让模型知道能拿到什么。

### 运行与校验

- 函数列表每行有 **「运行」**：填参即跑，显示**返回值**与**实际入参**（不写任何数据）
- 弹窗底部 **「校验定义」**：保存前先查（未知变量、未知内置函数、聚合配置、URL、模型等）
- 保存时后端**也会再校验一次**；工作副本审核阶段同样会拦

### Agent 接线

`tool_description` → 工具说明；`parameters` → 工具入参 schema（含 `required`）；
聚合/HTTP/模型形态会**自动追加 `object_key` 入参**用于定位对象。
调用结果返回 `{code, name, kind, result, outputs}`。

### 已知边界

- 不能调用另一个函数（无组合）
- 聚合的关系链最多 3 层，`limit` 1–100
- HTTP：只允许 http/https，超时 0.5–60 秒，请求体 ≤20KB
- 模型调用失败会把上游错误原文带回来（如配额超限的 429）



## 五之七、决策：把"决策"也当成数据（P3 新增）

> 官方的总命题是「本体表示**决策**，不只是数据」。P3 之前我们只有 `ai_action_log`
> ——记录的是"动作执行了、结果 success/noop"，**记录的是动作，不是决策**。

### 决策数据 = 三部分

官方原文把决策数据定义为 *"the context surrounding a given decision, the different options
evaluated, and the downstream implications of the committed choice"*。我们逐项落地：

| 官方 | 界面位置 | 说明 |
|---|---|---|
| **决策上下文** | 详情抽屉 →「决策上下文（依据）」 | 9 种依据：对象实例 / 对象属性 / 关联对象 / 函数结果 / 指标 / 本体版本 / **上游决策** / 外部数据 / 人工判断。会存**当时的取值快照** |
| **评估过的选项** | 详情抽屉 →「评估过的选项」 | 每个选项含评分、预计影响、**落选原因**、是否采纳。被否决的方案也要记 |
| **下游影响** | 详情抽屉 →「下游影响」 | **执行前后自动对目标对象做差**，给出 `字段: 旧值 → 新值`，标「自动」 |

### 决策谱系 = 三要素（都是自动捕获）

官方原文：*"of **when** a given decision was made, **atop which version of enterprise data**,
and **through which application**, is automatically captured"*。

| 要素 | 字段 | 怎么来的 |
|---|---|---|
| **何时** | 提出时间 / 拍板时间 / 执行时间 | 各阶段自动打点 |
| **基于哪个数据版本** | 数据版本 | 自动取该对象类型**已发布的最高版本**；也可手填 |
| **经由哪个应用** | 来源入口 | 本体控制台 / 智能体 / 外部接口 / 自动化 / 导入 |

### 决策生命周期

```
提出(proposed) → 拍板 → approved / rejected → 执行(executed) → 记录事后结果
```

- **提出**：左导航「决策」→「提出决策」。可以不指定动作（纯记录型决策）
- **拍板**：只有待决状态能拍板；拍板人、时间、意见都会留档
- **执行**：走**动作层的七道闸**（提交条件/值类型/规则/白名单/审批/副作用/审计），不另起一套；
  执行后自动捕获影响并弹出对比
- **事后结果**：记录指标的事前预期 vs 实际结果，会同时写入「下游影响」

### 决策是本体里的一等公民

`POST /ontology/decision/init-object-type` 会把「决策」注册为**对象类型**（后备表 `ai_ont_decision`，16 个属性）。
首次访问决策页时会自动注册一次。于是：

- 决策出现在**对象探索**里，可搜索、可翻页
- 决策可作为**关系的一端**（如 摄像机 ← 决策）
- 决策可被**函数/派生属性**作用
- Agent 可查询决策历史

### 决策→决策：让决策复利

在依据里填 `{"kind":"decision","ref":"dec_xxx"}` 并引用另一条决策编码，就形成了
「**每个决策为下一个决策提供依据**」的谱系链。

- 列表页「谱系」按钮：递归展示上游依据 + 下游影响 + 上游/下游决策
- 「谱系图」按钮：以决策为节点、依据与影响为边的网络图
- **被引用的决策不允许删除**（否则谱系会断），会提示是哪些决策在引用它

### Agent 接线（官方那条"智能体提决策 → 人工拍板"）

给 Agent 加了三个工具：

| 工具 | 作用 |
|---|---|
| `list_ontology_decisions` | 查历史决策（回答"以前类似情况怎么处理的"） |
| `get_decision_lineage` | 看某条决策的完整谱系（上游依据 + 下游影响） |
| `propose_decision` | **只登记为待决**，不会直接执行；必须写 rationale 与 evidence |

来源入口会自动记成「智能体」，人工在决策页拍板后才可执行——与官方
*"the agent's proposed decision is handed off to a human analyst for final review"* 一致。

### 两条硬校验

- **对象与动作必须指向同一个对象类型**：否则执行时前后快照会取错对象，捕获到的"下游影响"就是假的
- **编码唯一**：中文标题推不出 ASCII 片段，此时用标题摘要 + 时间戳，并自动追加 `_2`/`_3` 避免同秒冲突

### 已知边界

- 只做到"记录与可追溯"，**还没做**把决策历史蒸馏成原则反哺 Agent（官方的 decision-centric learning）
- 决策不是场景（scenario）：不能"暂存为假设"再对比

## 五之八、对象权限：两层授权 + 单元格级安全（P4 新增）

> 官方把本体授权分成**两层**：*"ontology resources, and objects and links"*。
> 资源和数据要分开看：**看得到类型 ≠ 看得到数据**。

### ① 本体资源权限（模式层）

对象类型 → **安全** → 「本体资源权限」。控制谁能**看到/编辑/管理这个对象类型的定义**。

三组角色（空 = 公开，保持既有行为不变）：

| 组 | 含义 |
|---|---|
| 可查看角色 | 能否看到这个对象类型（schema、联系人），**与能否看到数据无关** |
| 可编辑角色 | 能否改它的属性/关系配置 |
| 可管理角色 | 能否改它的权限策略本身；也是「策略属性」编辑所需 |

> **与官方的差异**：官方用 Compass **项目**做资源权限。我们没有文件系统，
> 因此实现官方文档里并列的**旧模型「Ontology roles」**（viewer/editor/owner）。

### ② 行级安全策略（对象安全策略）

决定**用户能读到哪些对象实例**。表达式语法：

| 可用 | 写法 |
|---|---|
| 对象属性 | 直接写列名，如 `location`、`dept_id` |
| 当前用户 | `user.id` / `user.name` / `user.dept` |
| 用户属性 | `user.attribute('dept_code')`（等价官方 `user.userAttribute(...)`） |
| 角色判断 | `user.role('ADMIN')` |
| 逻辑与比较 | `and` / `or` / `not` / `in` / `==` / `!=` / `<` `>` `<=` `>=` |
| 内置函数 | `len` `str` `int` `float` `lower` `upper` `contains` `startswith` `endswith` `any` `all` `min` `max` |

示例：`location == user.attribute('dept_code')`（只看本部门的设备）

判定规则：

- **超管直通**
- 没有任何启用的**允许**策略 → 全部可见（不破坏既有数据）
- 命中任一**拒绝**策略 → 拒绝（拒绝优先）
- 有允许策略时，必须命中至少一条

> **只在读时生效**（与官方一致）：过滤的是"用户能读到什么"，不改变底层数据，
> 也**不会传播到下游导出**。安全边界要保证的话，官方建议配合标记/分类。

### ③ 列级安全（属性可见角色）

同一页的「列级安全」表：给每个属性配**可见角色**（空 = 所有人可见）。
不可读的列会在所有读路径上被**掩掉**，不只是界面隐藏。

> 这个字段（`ai_ont_property.roles`）在 P4 之前**只存不用**——界面上能填，但没有任何过滤生效。
> 现在它真正参与读与写的判定。

### ④ 策略属性（官方 edit policy property 的等价物）

被行级策略**引用**的属性（如上面例子里的 `location`）改动会影响可见性，
因此需要**管理角色**才能改。若对象类型没配管理角色，安全页会给出**加固提示**。

### ⑤ 检查访问权限（对齐官方 Check access 面板）

选一个用户 + 一个对象主键 → 逐步给出判定：

```
对象类型可见性   → 通过 / 拒绝（缺哪个角色）
列级安全         → 有几个属性不可读、是哪些
行级安全         → 命中/未命中哪条策略
策略属性         → 哪些属性编辑需要管理权限
```

这是"**为什么他看不到这条数据**"的答案，而不是一个 true/false。

### ⑥ 强制点在哪（重要）

权限不只挡界面，这些路径都过：

| 路径 | 行为 |
|---|---|
| 实例搜索 | 按行策略过滤，按列策略掩列（返回里会标 `policy_filtered`） |
| 单条实例 | 行策略不过直接拒绝 |
| **关联跳转 / 实例图** | 同样过滤——否则能从看得见的对象跳到看不见的 |
| 属性写回 | 行策略 + 列策略 + **不能写自己都读不到的列** + 策略属性需管理权 |
| 动作执行 | 官方规则：**动作类型 + 动作所编辑的对象类型**都要有编辑权 |
| **Agent 工具** | 按调用者权限过滤工具列表、并拒绝越权调用（见下） |

> **Agent 那个口子是 P4 之前的最大问题**：`run_ontology_tool` 收了 `user_id` 却**完全没用**，
> Agent 能绕过数据权限读任何对象、调用任何动作。现在：
> 生成工具时就过滤（看不到的资源**连"知道它存在"都不行**）、调用时再校验一次。

### 已知边界

- 没做**标记（markings）**与**目的（purpose）**：我们用"角色"近似，粒度更粗
- 没做**基于分类的访问控制（CBAC）**
- 没做**多数据源对象类型（MDO）**：不能按数据源分别授权
- 未配置 ACL = 公开（为了不动既有数据），因此**默认不是拒绝式**安全
- 行策略是**逐行在应用层求值**，大数据量下会退化为全表扫描后过滤



## 五之九、场景：沙箱式"假设分析"（P5 新增）

> 官方定义（当前 Beta 版，非 legacy 的 Workshop 版）：
> *"A scenario is essentially a **sandbox to apply edits on top of the data in your Ontology**,
> generated by applying one or more actions."*

### 场景是什么

**一个场景 = 一组「相对基线的差异」**。在场景里执行动作，**不会写真实数据表**，
只把差异记进场景。读取场景时看到的是 **基线数据 + 场景差异**。

```
真实数据（基线）
   └─ 场景A：name 改成 "A方案"      ← 只存在于沙箱
   └─ 场景B：name 改成 "B方案"      ← 只存在于沙箱
合并场景A → 真实数据才变成 "A方案"
```

> 官方强调：场景**不是数据版本工具**，不能用来做历史时点快照。

### 怎么用

左导航 **「场景」**：

| 操作 | 说明 |
|---|---|
| **新建场景** | 可指定「合并动作」与「可编辑范围」（留空 = 不限制）；寿命默认 **31 天** |
| **在场景内执行动作** | 接口带 `scenario` 参数（`POST /ontology/action/execute` 的 `scenario` 字段）即进入沙箱 |
| **详情** | 展示「合并后会变成什么」：逐对象的 `字段: 旧值 → 新值`，以及来源动作 |
| **合并** | **单事务**写入真实表，任一失败全部回滚；合并权限由**合并动作的提交条件**决定 |
| **丢弃** | 编辑不生效 |
| **复制** | 连编辑一起复制（官方支持 duplicate） |
| **对比选中** | 多场景并排看同一对象的不同取值 |

### 官方限额（都已强制）

| 限额 | 值 |
|---|---|
| 单个场景的编辑数 | **30,000** |
| 单个场景的动作数 | **50** |
| 从对象集加载 | **10,000** 个对象 |
| 默认寿命 | **31 天**（到期自动删除并清空编辑） |

### 模型预测不会被合并

官方：*"Model results in a Scenario will **not** be applied to the Ontology as these represent
expected results rather than explicitly modifiable values."*

场景详情里模型预测结果会**单独列出并标注**，合并时跳过。

### 按执行上下文治理动作（重要）

这是场景与 P0 那个执行上下文的接合点。官方：
*"Action submission criteria can distinguish between actions executed within a scenario and
actions executed against the main Ontology."*

于是可以给动作写这样的提交条件：

```json
[{"operator":"is","failure_message":"该动作只允许在场景内试跑",
  "left":{"kind":"execution_context","value":"is_scenario"},
  "right":{"kind":"static","value":true}}]
```

**实测**：不带场景执行 → 被拦下「该动作只允许在场景内试跑」；带场景执行 → 通过。
这样就能**放心给规划者和智能体更宽松的试跑权限**，而把「合并到主本体」单独用
合并动作的提交条件管住。

### 我们与官方的一处差异（更简单且等价）

官方在底层复制一份数据、并**每 10 分钟自动 rebase** 到基线之上。
我们存的是**相对基线的差异集**，读的时候叠加——因此**天然总是基于最新基线数据**，
等价于官方的自动 rebase，而且不需要定时任务、也不存在 rebase 冲突。

### 已知边界

- **未做**场景持久化为对象（官方的 persisted scenario）
- **未做**按 link type 的细粒度范围（只做了 object types 范围）
- **未做**场景级权限隔离（场景内执行仍走调用者本人的对象权限）

## 五之十一、问数怎么用本体的权限和语义（本轮新增）

**一句话**：问数就是**读**，所以它不该另搞一套权限——它复用本体的行级/列级策略。

### 为什么不是"外面套一层 WHERE"

问数的 SQL 是**运行时任意形状**的（聚合 / 分组 / 多表 join）。
如果只在最外层加 `WHERE`，**聚合会把不该看的行也算进去**。所以本体的做法是
把表引用整体改写成**已过滤的子查询**：

```sql
-- 问数生成的
SELECT dept, sum(amount) FROM demo_sales GROUP BY dept
-- 改写后（过滤发生在聚合之前）
SELECT dept, sum(amount) FROM (
    SELECT * FROM demo_sales WHERE (dept = 1)
) AS demo_sales GROUP BY dept
```

### 怎么看效果

载入演示数据后，用**不同部门身份**问同一个问题：

| 问数问题 | 部门 1 的人 | 部门 2 的人 | 超管 |
|---|---|---|---|
| 各部门销售额 | `1 → 38000` | `2 → 32000` | `1→38000, 2→32000` |
| 订单数 / 总额 | **4 笔 / 38000** | **4 笔 / 32000** | **8 笔 / 70000** |

**聚合被真的过滤了**——部门 1 看到 38000 而不是 70000。这是 `secure_sql` 下推的结果。

### 策略能翻译成 SQL 的写法

| 策略写法 | 翻译成 |
|---|---|
| `dept == user.attribute('dept_id')` | `("dept" = 1)` |
| `status in ('ONLINE','OFFLINE')` | `("status" IN ('ONLINE','OFFLINE'))` |
| `contains(name, '东门')` | `("name" LIKE '%' \|\| '东门' \|\| '%')` |
| `len(name) > 2` | `(LENGTH("name") > 2)` |
| `a and not (b == 2)` | `(("a") AND (NOT ("b" = 2)))` |
| `user.role('ADMIN')` | `TRUE` / `FALSE`（按用户求值成常量） |

### 翻不了就拒绝（fail-safe）

如果一条策略**翻译不成 SQL**（用了不支持的语法、引用了表里没有的列），
`secure_sql` 会**拒绝执行这条查询**，而不是放行未过滤的结果。
理由很直白：宁可查不出来，也不能让人看到不该看的。

> 另外有**第一道防线**：`upsert_row_policy` 在保存时就会做语义校验，
> 引用了不存在列的策略根本存不进去。上面说的是第二道防线（万一库里已有）。

### 关系（join 路径）也进了 prompt

NL2SQL 最容易出错的是**多表关联靠猜**。现在本体把显式关系注入提示词：

```
【本体关系（写多表查询时按此 join，不要靠字段名猜）】
- 「告警记录表」video_alarm_records.camera_id = 「摄像机表」video_cameras.id
    关系名：摄像机，基数：many_to_one
```

**并且用的是真实支撑表名**（`video_cameras`，不是 `ont_video_cameras`）——
之前这里拼错过前缀，会让 LLM 照着一个不存在的表名写 SQL。

### 本轮顺带修掉的三个既有缺陷（都是问数跑不通的真原因）

排查时发现问数**一直在失败**，而且失败信息完全看不出原因。三个真原因：

| # | 缺陷 | 表现 |
|---|---|---|
| 31 | `_nl2sql` 构造模型客户端时**没注入网关请求头**（同文件另两处都用了 `build_headers`，这里漏了） | opencode 网关返回错误文本，被当成 SQL 去校验 → 报「仅允许 SELECT 查询」 |
| 32 | `_extract_sql` 没处理工具化 Agent 要求的 **JSON 输出**（`{"sql": "..."}`） | JSON 尾部 `"}` 留在 SQL 里 → sqlglot 解析不出 Select → 同样报「仅允许 SELECT 查询」 |
| 33 | 可查询白名单只拼 `ont_{code}`，而**支撑表常是原表名**（`video_cameras` / `demo_sales`） | 报「表 xxx 不在可查询白名单内」，本体支撑的表根本查不到 |

另外 `_get_runtime` 有个选择顺序问题：`get_runtime_model('query')` 会把 **`usage` 为空**的模型
也算命中（"通用"语义），于是专门配的本地 chat 模型根本不参与，问数被顶到那个通用模型上。
现在改为**精确匹配用途优先**。

> 第 31 条已用 `git stash` 回退验证过：**原始代码报一模一样的错**，不是我改出来的。

## 五之十二、语义收敛：本体是唯一语义源（本轮新增）

### 为什么要收敛

问数原先有 **9 处直接拼 SQL 读 `ai_ont_*` 表**，没有任何契约。
本体表结构一改，问数就可能悄悄坏掉——这正是"看起来接上了，实际靠约定"。
而且它自己还养了一套重复语义（`ai_query_concept` / `ai_query_metrics` /
`ai_query_dictionary` / `ai_query_schema`），**同一个字段在两边可能一边标敏感、一边没标**。

### 现在怎么做

本体新增统一语义接口 `ontology/semantic.py`，**消费方只调它**：

| 接口 | 作用 |
|---|---|
| `object_table_map()` | 真实支撑表名 → 对象 code（白名单 / SQL 改写用） |
| `semantic_context()` | 对象 / 属性 / 关系 / 函数 / 概念，一次拿全 |
| `context_block()` | 渲染成 prompt 文本块（问数直接用，不再自己拼表名） |
| `sensitive_fields()` | **唯一的**敏感字段来源 |
| `sensitive_diff()` / `sync_sensitive()` | 两套标记的差异与对齐 |

**结果**：问数里直连读本体表的地方 **9 → 0**（只剩 3 处**写**路径，那是
"从数据源反向生成本体"，本来就该由它写）。

### 敏感标记对齐（真实不一致，已修）

| | 对齐前 | 对齐后 |
|---|---|---|
| 本体标记 | 9 | 9 |
| 问数标记 | 2 | 9 |
| **两边一致** | **0** | **9** |

对齐前的两套各标各的：
- **仅本体**：`sys_user.password`、`ai_models.api_key`、`ai_providers.api_key`、
  `ai_query_datasources.password`、`ai_workflows.share_token`、`train_deploys.api_key` …
- **仅问数**：`ai_call_logs.prompt_tokens`、`completion_tokens` ← **这是误报**

误报根源：扫描器规则里 `"token"` 用**子串匹配**，把 `prompt_tokens`（计数）
也当成了令牌——和之前 `tokenizer_model` 被标成密钥是同一类问题。
现在加了 `NOT_SECRET` 排除表，并让扫描器**把结果同步回本体**（本体是唯一真相源）。

### 已知边界

- `ai_query_metrics`（15 条，可参数化 SQL 模板）与 `ai_query_fewshot`（问答样例）
  **保留在问数**——它们确实是问答独有的，不是重复语义。
- `ai_query_dictionary`（24 条术语映射）暂未迁走，但已能通过统一接口读到。
- 语义收敛只做了**读路径**；那几张表的**物理清理**（迁数据 / 删表）没做，
  因为要迁数据、风险比读路径高，按"先加接口层、观察后再迁"的顺序留着。

## 五之十三、问数的精准与速度（本轮专项）

### 先看数字（同一套 98 题金标集，前后对照）

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| **结果数据精度** | 88.8% | **95.9%** | **+7.1pp** |
| **全程 P50** | 9886 ms | **3410 ms** | **快 2.9 倍** |
| **缓存命中 P50** | — | **~140 ms** | **快 70 倍** |
| 快路径（指标模板）P50 | 151.9 ms | 150.2 ms | 持平 |
| 快路径语义精度 | 100% | 100% | 持平 |

标注 75%→**100%**、用户 67%→**100%**、设备 67%→**100%**。

### 瓶颈是怎么找到的

先量阶段耗时，再动手。实测单题拆解：

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| LLM 生成 | 7055 ms | **3147 ms** |
| SQL 执行 | 18 ms | 17 ms |
| 收尾 | 1802 ms | **30 ms** |

**两个真瓶颈**（都不是"模型慢"这么简单）：

1. **工具往返 7.25 次/题** —— 工具化 Agent 挂了 15 个工具、`tool_call_limit=6`，
   而**每次工具调用都是一轮 LLM 往返**。可它提供的信息（表结构/枚举值/few-shot/
   join 路径/代价护栏/执行校验）**本地检索与本地执行已全覆盖**，纯亏。
2. **prompt 全量倾倒** —— 本体块把**全部 85 个对象、1501 个属性**都塞进去，
   实测 **37517 字符**。LLM 的前缀计算大半花在与问题无关的对象上。

### 做了什么

**快速**

| 改动 | 效果 |
|---|---|
| 关掉工具往返（`agno_tool_agent=false`，可随时改回） | 每题 LLM 往返 7.25 → **1~2 次** |
| 本体块**按问题检索过滤**（只带命中表） | 37517 → **千余字符**；LLM 生成 7055→3147ms |
| **SQL 缓存**（键=归一化问题+数据源，TTL 30 分钟） | 重复提问 **~140ms** |
| **检索记忆缓存**（同一问题一次问答里被检索两次） | 收尾 1802 → **30ms** |
| `ask()` 里指标/术语**不再重复加载**（慢路径里又查一遍） | 少两次库查询 |

> **缓存为什么只缓存 SQL、不缓存结果行**：结果必须按调用者身份重新执行——
> 行级/列级策略是在执行时下推的（`secure_sql`）。一旦缓存结果行，
> **A 看到的数据会被 B 拿到**。这是"快"与"安全"的边界，不能含糊。

**精准**

| 改动 | 说明 |
|---|---|
| 修**支撑表解析自相矛盾** | `backing_table` 为空时，`semantic_context` 回退成 `code`（指向不存在的表），而 `object_table_map` 按 `ont_{code}` —— **我自己的两个函数打架**。改成按库里实际存在哪张表来定 |
| **LIMIT 确定性放宽** | 问题要"每个/各/所有"全量列举时，模型常自作主张加小 LIMIT（实测把 216 行截成 50 行 → 判错）。改为放宽到上限 |
| **"取前 N"不放宽** | 上面那条第一版把 `各算法类型的平均延迟，**取前5名**` 也放宽了（含"各"），5 行变 1000 行 → 基准立刻从 ✓ 变 ✗。**这是我自己引入的回退，靠复测抓出来的** |
| 修金标集 | `本体对象` 那 5 题原本指向**已软删**的 `orders`/`customers` 对象，恒为 20%，量的是不存在的东西 |

### 已知边界（诚实说明）

- **剩余 4 题失败**：`统计每个摄像头各类告警的数量`、`每个摄像头组下各有多少摄像头`、
  `各小时的告警分布`（基线也失败）、`各框架下的训练模型数量`（`train_models` 表 **0 行**，
  金标本身没有可对的数据）。
- **P50 3410ms 的下限是模型本身**：一次生成约 3.1 秒，这是本地 284B 模型的速度。
  想再快只能换更小/更快的模型，或提高快路径（指标模板）覆盖率。
- **SQL 缓存是进程内的**，不跨 worker、重启即失效。多副本部署需要换成 Redis。
- **缓存 TTL 30 分钟**：口径/schema 变化靠 TTL 兜底，没有做主动失效。
- **金标集我改过**（`本体对象` 那 5 题）：原题留档在 `benchmark.py` 注释里，
  改的是"指向已删对象"的失效题，不是放宽判定标准。

### ⚠️ 一个我引入的、还没收干净的回退（诚实说明）

**prompt 长度直接决定生成耗时**（实测 12758 字符→3432ms；15690 字符→7569ms；
而模型对极小请求只要 200-550ms —— 所以慢的不是模型，是 prompt）。

我加的**别名检索**会往 prompt 里多补最多 3 张表的字段，把 schema 段撑大。
前后对照（同一套 98 题）：

| 版本 | 精度 | P50 |
|---|---|---|
| 优化后最好的一版（**无**别名检索） | **95.9%** | **3410 ms** |
| 加了别名检索（不限量、含对象名） | 93.9% | 6770 ms |
| 加了别名检索（限 3 张、仅别名） | 94.9% | 6030 ms |

**结论：别名检索目前是「花了 prompt 长度、没换来精度」。** 它确实修好了
「销售额 → 销售订单」这一个场景，但整体上不划算。

**我没能做完的事**：干净地 A/B 一次（每次全量约 7 分钟，期间本地模型负载会漂移），
所以**无法 100% 断定差异全部来自别名检索**。下一步该做的是把它做成配置项，
跑一次「开/关」对照再决定去留。

#### 筛选器（真的会筛）

在「编辑」里加一个**筛选器**组件，再在同一标签页放**对象表格**或**关联对象**组件——
筛选条件就会作用于它们。渲染时标签页顶部会有一条提示写明**本标签页生效的筛选**。

支持的算子（与实例层**同一套词表**）：

| 算子 | 含义 |
|---|---|

| `is_empty` / `not_empty` | 为空 / 不为空 |

> （`test_filter_ops_are_a_single_vocabulary`）。

### B) 索引

-- 建索引后，Postgres 里真的多了一个索引

|---|---|

### 已知边界（诚实说明）

- **对象视图**：未做 apps/files 类 widget；共享做到了「跟随对象类型 / 按角色」，但**未做 marketplace 式发布**；深链只支持视图 + 对象主键，未支持"带当前筛选条件"的链接
- **索引**：未做真正的 Funnel 流水线（我们是同步构建）；**全文索引的 gin 索引仅 Postgres 支持**，
  其它方言会退回普通索引；streaming 的 2 MB/s 限流只是常量记录，未实际限流
- **提案**：未做"基于另一个提案建分支"的禁止校验（我们本来就没有父分支概念）；
  未做任务级评论侧边栏（评论接口已有）
- **跨库移植性**：实例层（读/写/权限/场景）原先大量使用 Postgres 专属写法
  （`::text`、`ILIKE`、`information_schema`、`pg_total_relation_size`），
  A/B/C 期间已改为跨方言（`_cast_text` / `_ilike` / SQLAlchemy 反射 / 方言守卫），
  但**仍以 Postgres 为第一支持目标**；SQLite 上部分路径未完整验证

## 七、几条设计约束（避免踩坑）

1. **导入是幂等的**：重复导入同一张表会按当前结构重建属性，不会像旧实现那样累加重复属性。
2. **回填尊重人工编辑**：只有「名字还等于编码」「描述还是占位符」「类型还不是 enum」时才覆盖。
3. **删除本体不会删对象**：对象退回「未分组」，对象本身保留。
4. **动作只支持 `update`**：`insert` / `delete` 尚未实现，调用会被拒绝。
5. **函数不支持 SQL**：见第三节第 4 点。
6. **对象名 ≠ 表名是好事**：`video_cameras` 显示成「摄像机表」才有业务含义；没有表注释的 28 个对象仍是表名，补上注释再跑回填即可。
