> 失败原因里，模型确实是因为「不知道这张表是什么」而选错表；问题在于**选表发生在召回阶段**，
> 提示词里出现描述时表已经选错了——描述来得太晚。

## 四、A 臂 16 条失败归因

| 类别 | 条数 | 现象 |
|------|------|------|
| **指标快路径误劫持** | 6 | 「配煤方案分仓明细」→ `配煤方案数量`；「供应商煤质限制」→ `供应商数量`；「配煤结果」→ `配煤方案…`；且指标 SQL 不带 `ISDELETED`（计数 5 vs 4） |
| **表消歧失败** | 7 | 「期初库存明细」→ `INVENTORYREPORTDETAIL`（应为 `STORAGEINITIALIZEDETAIL`）；「成本项目」→ `FACTORYCOSTYEAR` / `SYS_CODES` / `JIMU_DICT_ITEM`；「期初库存主表」→ 明细表 |
| 我方金标过严 | 1 | 「取前 3 个单据号」题面没写并列规则，金标加了 tie-break |
| 其它 | 2 | 空 SQL / 聚合口径不同 |

**真正的短板是两件事**：
1. **指标匹配把「通用词重合」当成「同一张表」**（计划/明细/数量/供应商）→ 快路径直接给错数，且不经过软删口径；
2. **召回阶段分不清同族表**（主表/明细、方案/方案明细、年份/项目），提示词里的描述救不回来。

## 五、下一步（C 臂）

1. **指标护栏**：绑定型指标（绑定到某张表的 count/avg）必须与问句在**该表的中文名/别名**上有重合，否则不参与快路径；通用词（计划/明细/数量/条数/记录/表/平均…）不算证据。
2. **软删口径**：指标快路径的 SQL 也要补 `ISDELETED = false`（现在只有慢路径补）。
3. 表消歧要**在召回层**解决（别名/描述参与检索打分），不是往提示词里加字。

验证纪律：v1 不复跑；v2 的 A/B 已完成并冻结；C 臂改完用 v2 复跑 + 105 题回归，结果标注「v2 题目已看过」。

## 六、C 臂：指标护栏（已实测，**判定负收益，代码已回退**）

思路：绑定型指标（绑定到某张表的 count/avg）必须与问句在**该表中文名/别名**上有证据，
否则不参战；同时给「多少条」这类计数诉求加一条「非计数指标不参战」。

试验了两种口径（都无其他改动，描述注入保持关闭）：

| 臂 | 规则 | v2 准确率 | 105 准确率 | 105 快路径 |
|----|------|-----------|------------|------------|
| A | 无护栏 | 21/37 = 56.76% | 104/105 = 99.05% | 31.43% |
| C-宽 | 所有绑定型指标都要表证据 | 24/37 = **64.86%** | 104/105 = 99.05% | **20.95%**（11 条被推去慢路径） |
| C-窄 | 只拦计数型 + 计数诉求排除非计数指标 | 22/37 = 59.46% | **103/105 = 98.10%** | 26.67% |

**C-窄为什么反而更差**：护栏把「咱们一共有多少份燃煤合同」的正确计数指标挡掉了
（该表的中文名覆盖不全/对不上），于是 `contract_amount_sum`（金额合计）赢了快路径 ——
**拦对了误劫持，也误伤了原本正确的题**。C-宽则把「当前煤场库存量」这类 sum 指标一起拦掉，
11 条正常快路径退化到慢路径，准确率没涨、延迟大涨。

结论：**在现有资产中文名覆盖度下，靠"匹配规则"修劫持是负收益**。真正该做的是：
1. 修**指标本身**：绑定型 `count` 指标的执行口径补 `ISDELETED = false`（实测
   「采购计划主表有多少条」指标给 5、实际有效 4）；把指标命名成业务名（现在有
   「配煤方案结果明细表STOQTY合计」这种把表名+字段名拼起来的名字）。
2. 修**往返路径**：拦住劫持后慢路径仍然选错同族表（供应商煤质限制 → 供应商管理），
   所以必须先解决表消歧，护栏才有意义。

代码已 `git checkout` 回退；两个数字（v2 64.86% / 105 98.10%）作为"此路不通"的证据保留。

## 七、修复：绑定型指标补软删口径（已上线）

`instance_aggregate` 新增 `exclude_deleted`（默认关闭，只由**指标快路径**打开）：
对象支撑表存在 `ISDELETED` 列时，聚合前追加 `"ISDELETED" = false`。
为什么默认关：对象浏览/图表看的是全量，口径不该被指标路径的需求改动。

| 验证 | 修复前 | 修复后 |
|------|--------|--------|
| 指标 `FUEL_CMCS_PURCHASEPLAN_count_ID` | 5（含 1 条软删） | **4**（库内有效行=4） |
| 无 `ISDELETED` 的表（供应商煤质限制） | 7 | 7（未受影响） |
| 问「采购计划主表一共有多少条记录」 | fast，答 5（错） | **fast，答 4（对）** |
| holdout-v2 | 21/37 = 56.76% | **22/37 = 59.46%**（fixed 1 / regressed 0，快路径占比不变 8/37） |
| 105 题回归 | 104/105 = 99.05%，fast 31.43% | **完全一致** |

> 只 +1 题是符合预期的：这个缺陷只影响「问"有多少条"、且该表有软删行」的指标题。
> 它与 v2 里 6 条「指标劫持」不是一回事 —— 劫持要靠选表解决（见第六节：护栏是负收益）。
